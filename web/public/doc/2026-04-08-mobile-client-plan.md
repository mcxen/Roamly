# Roamly 移动端与同步方案

日期：2026-04-08

## 目标

本轮移动端建设目标分三块：

1. UIKit iOS 客户端，支持离线查看全部已同步地图
2. 连接 Roamly 服务端进行同步，支持移动端图片上传备份
3. 手机端支持搜索，搜索结果基于服务端已有 OCR 数据

## 现状

当前服务端已经具备：

- 地图列表分页：`GET /api/maps`
- 详情：`GET /api/maps/:id`
- 文件访问：`GET /api/files/:id`
- 上传：`POST /api/maps/upload`
- OCR 搜索：`GET /api/maps?q=关键词`
- OCR 状态：`GET /api/ocr/status`

这意味着：

- Roamly 已经具备“服务端图库”的基本能力
- 但还缺移动端友好的同步视图
- 也缺一个专门给手机客户端用的工程骨架

## 方案拆分

### 一、服务端补充移动端同步 API

新增移动端专用接口：

- `GET /api/mobile/manifest`
  作用：返回适合同步到手机本地的地图清单

- `GET /api/mobile/search`
  作用：按关键词搜索，显式说明它会命中服务端 OCR 文本

- `GET /api/mobile/maps/:id`
  作用：返回移动端详情，便于以后裁剪字段

这些接口不会替换现有 Web API，而是为 UIKit 客户端提供更稳定、字段更聚焦的契约。

### 二、UIKit iOS 客户端

客户端采用 UIKit + 原生本地缓存，先做以下模块：

- Library：离线地图列表
- Search：服务端搜索
- Detail：查看已缓存原图
- Settings：配置服务端地址、触发同步、查看同步状态

数据策略：

- 元数据清单缓存到本地 JSON
- 原图文件缓存到 App 沙盒
- 详情优先读取本地原图，未命中时尝试在线读取

### 三、移动端图片备份

移动端备份先复用现有上传能力：

- 用户从相册选择图片
- 客户端上传到 `POST /api/maps/upload`
- 服务端继续走当前扫描、缩略图预热、OCR 队列

后续如果需要“自动后台备份”，再单独设计增量上传与冲突处理。

## 同步模型

第一版采用“全量 manifest + 客户端增量下载文件”的简单模型：

1. 客户端请求 `GET /api/mobile/manifest`
2. 对比本地已缓存地图 `id + updated_at + mtime_ms`
3. 缺失或变更的地图重新下载原图
4. 本地不存在于 manifest 的地图标记为已删除并清理缓存

优点：

- 服务端改动小
- 不需要额外 tombstone 表
- 逻辑稳定，足够支持个人图库规模

## 搜索策略

### 在线搜索

移动端搜索调用服务端：

- `GET /api/mobile/search?q=杭州`

该搜索会命中：

- 标题
- 文件名
- 城市 / 国家 / 省份
- `ocr_text`

因此它满足“基于服务端 OCR 结果进行搜索”的目标。

### 离线搜索

第一版离线搜索只保证：

- 标题
- 文件名
- 国家 / 省份 / 城市

OCR 全量离线索引会显著增大缓存量，后续再视图库规模决定是否下放到本地。

## Web 端重绘方向

Web 管理端建议采用“编辑部档案馆”方向：

- 纸张底色
- 墨线边框
- 更强的层级标题
- 工具栏与内容区解耦
- 把上传、筛选、详情编辑拆成更稳定的模块

这会和历史地图整理场景更一致，也能和 iOS 客户端形成“档案系统”同一视觉语义。

## 本轮落地顺序

1. 文档沉淀到 `public/doc`
2. 服务端补充移动端 API
3. 创建 UIKit iOS 工程
4. 接入离线缓存、同步、搜索、详情
5. 重绘 Web 界面风格

## 风险

- “离线查看全部原图”会占用显著手机存储，需要后续增加容量提示
- OCR 离线全量索引暂时不做，第一版保留服务端 OCR 搜索
- 若未来做真正双向同步，需要增加删除记录和冲突策略

## 结论

Roamly 现有后端已经足够支撑移动端第一版。

缺的不是“再造一套系统”，而是：

- 一层移动端专用 API 契约
- 一个 UIKit 客户端
- 一套明确的离线缓存与同步模型

这三块打通后，Roamly 就会从“本地 Web 地图库”升级成“Web 管理端 + iPhone 离线浏览与备份客户端”的双端系统。
