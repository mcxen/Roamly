# Roamly 移动端与同步方案

日期：2026-04-08

## 目标

本轮移动端建设目标分三块：

1. UIKit iOS 客户端，支持离线查看全部已同步地图
2. 连接 Roamly 服务端进行同步，支持移动端图片上传备份
3. 手机端支持搜索，搜索结果基于服务端已有 OCR 数据

## 现状

当前服务端已经具备：

- 地图列表分页：`GET /api/maps`
- 详情：`GET /api/maps/:id`
- 文件访问：`GET /api/files/:id`
- 上传：`POST /api/maps/upload`
- OCR 搜索：`GET /api/maps?q=关键词`
- OCR 状态：`GET /api/ocr/status`

这意味着：

- Roamly 已经具备“服务端图库”的基本能力
- 但还缺移动端友好的同步视图
- 也缺一个专门给手机客户端用的工程骨架

## 2026-05-05 移动端功能更新

本轮 iOS 端已经从“同步查看客户端”推进到“移动端整理工作台”。新增能力主要集中在图库浏览、批量整理、AI 编目和地图范围校准。

### 一、图库与地图范围预览

- 图库页支持列表 / 平铺切换，并保留搜索、来源、未整理、收藏等筛选入口。
- 地图卡片增加 OCR、来源、本地状态、整理状态等标签，便于快速判断待处理项。
- 卡片右侧增加覆盖范围预览和经纬度范围摘要，用于快速检查地图是否已经完成地理校准。
- 覆盖范围字段扩展为 `north_latitude`、`south_latitude`、`east_longitude`、`west_longitude` 与 `coverage_outline`，其中 `coverage_outline` 是缩略图坐标系上的主体地图轮廓点，不是经纬度。

### 二、详情页范围/轮廓校准

- 详情页增加“AI 提取范围/轮廓”能力，可基于 OCR、文件名、已有元数据和缩略图提取经纬度外接框与缩略图轮廓。
- 轮廓编辑器支持点选、拖动、删除和清空，保存时会把轮廓与经纬度范围一并写回本地记录并同步到服务端。
- AI 返回的 `coverage_outline` 会先做归一化和退化校验，避免把经纬度外接框误画成缩略图中间的小矩形；明显过小或面积异常的轮廓会回退到地区保底轮廓。

### 三、整理页批量任务

- 整理页支持按“全部 / 待补地区 / 待补年代 / 待 OCR / 待 AI”筛选待处理队列。
- 批量操作包括：全选当前、清空、批量年代、批量地区、批量 OCR、AI 整理。
- 批量 OCR 改为复用底部全局进度条，不再用居中弹窗遮挡列表；状态会显示当前识别进度、待 OCR 数和待 AI 数。
- AI 批量整理使用同一条全局进度条，按基础信息、经纬度、缩略图轮廓分步推进，失败时保留错误提示。

### 四、AI 服务商与调试

- 设置页增加 AI 服务商配置，支持 DeepSeek、OpenAI 和 OpenAI-Compatible 接口。
- OpenAI-Compatible 模式要求填写供应商给出的精确模型 ID，避免误用默认模型。
- 支持从 `/models` 获取可用模型列表，并可测试 AI 延迟。
- AI 配置可保存为多个服务商条目并切换，便于在不同供应商之间调试。
- 新增 AI 对话历史，记录请求预览、响应预览和解析结果，方便定位模型输出不符合 JSON 或轮廓不准确的问题。

### 五、服务端与同步字段

- 服务端地图记录同步支持 `coverage_outline` 字段，移动端保存范围/轮廓后可通过现有保存流程写回。
- 移动端本地记录模型同步扩展经纬度外接框、轮廓、AI 编目字段和 OCR 状态，保证离线浏览和整理页筛选能直接使用本地缓存。

## 方案拆分

### 一、服务端补充移动端同步 API

新增移动端专用接口：

- `GET /api/mobile/manifest`
  作用：返回适合同步到手机本地的地图清单

- `GET /api/mobile/search`
  作用：按关键词搜索，显式说明它会命中服务端 OCR 文本

- `GET /api/mobile/maps/:id`
  作用：返回移动端详情，便于以后裁剪字段

这些接口不会替换现有 Web API，而是为 UIKit 客户端提供更稳定、字段更聚焦的契约。

### 二、UIKit iOS 客户端

客户端采用 UIKit + 原生本地缓存，先做以下模块：

- Library：离线地图列表
- Search：服务端搜索
- Detail：查看已缓存原图
- Settings：配置服务端地址、触发同步、查看同步状态

数据策略：

- 元数据清单缓存到本地 JSON
- 原图文件缓存到 App 沙盒
- 详情优先读取本地原图，未命中时尝试在线读取

### 三、移动端图片备份

移动端备份先复用现有上传能力：

- 用户从相册选择图片
- 客户端上传到 `POST /api/maps/upload`
- 服务端继续走当前扫描、缩略图预热、OCR 队列

后续如果需要“自动后台备份”，再单独设计增量上传与冲突处理。

## 同步模型

第一版采用“全量 manifest + 客户端增量下载文件”的简单模型：

1. 客户端请求 `GET /api/mobile/manifest`
2. 对比本地已缓存地图 `id + updated_at + mtime_ms`
3. 缺失或变更的地图重新下载原图
4. 本地不存在于 manifest 的地图标记为已删除并清理缓存

优点：

- 服务端改动小
- 不需要额外 tombstone 表
- 逻辑稳定，足够支持个人图库规模

## 搜索策略

### 在线搜索

移动端搜索调用服务端：

- `GET /api/mobile/search?q=杭州`

该搜索会命中：

- 标题
- 文件名
- 城市 / 国家 / 省份
- `ocr_text`

因此它满足“基于服务端 OCR 结果进行搜索”的目标。

### 离线搜索

第一版离线搜索只保证：

- 标题
- 文件名
- 国家 / 省份 / 城市

OCR 全量离线索引会显著增大缓存量，后续再视图库规模决定是否下放到本地。

## Web 端重绘方向

Web 管理端建议采用“编辑部档案馆”方向：

- 纸张底色
- 墨线边框
- 更强的层级标题
- 工具栏与内容区解耦
- 把上传、筛选、详情编辑拆成更稳定的模块

这会和历史地图整理场景更一致，也能和 iOS 客户端形成“档案系统”同一视觉语义。

## 本轮落地顺序

1. 文档沉淀到 `public/doc`
2. 服务端补充移动端 API
3. 创建 UIKit iOS 工程
4. 接入离线缓存、同步、搜索、详情
5. 重绘 Web 界面风格

## 风险

- “离线查看全部原图”会占用显著手机存储，需要后续增加容量提示
- OCR 离线全量索引暂时不做，第一版保留服务端 OCR 搜索
- 若未来做真正双向同步，需要增加删除记录和冲突策略

## 结论

Roamly 现有后端已经足够支撑移动端第一版。

缺的不是“再造一套系统”，而是：

- 一层移动端专用 API 契约
- 一个 UIKit 客户端
- 一套明确的离线缓存与同步模型

这三块打通后，Roamly 就会从“本地 Web 地图库”升级成“Web 管理端 + iPhone 离线浏览与备份客户端”的双端系统。
